04 — Assessment Pipeline

End-to-End Vulnerability Assessment

Six-stage pipeline from on-node collection to validated remediation. Assessment is cloud-side — zero computation on Vault nodes.

01

Collection

Agent collects RPM inventory, process list, network connections, system info from Vault RHEL 9 node

Every 6h / 15m / 24h
02

Transport

JSON payload encrypted via TLS 1.2, authenticated with org-specific client certificate, TCP/443 outbound

~50–200 KB per cycle
03

Assessment

Rapid7 cloud matches RPM versions against continuously-updated vuln DB (NVD + RHSA + HCSEC + Go DB)

Minutes after receipt
04

Sync

InsightVM Console pulls agent findings from Platform. Risk scored with Active Risk model (CVSS + exploitability)

Every 2h (configurable 1–12h)
05

Remediation

Jira ticket auto-created per finding. Platform Eng patches via Ansible. E8 SLA clock tracked in InsightVM

48h / 2 weeks / 1 month SLA
06

Validation

Agent re-collects RPM inventory within 6h. Cloud re-assesses. If CVE persists, Jira ticket reopened

Auto-validated within 6h

06 — Architecture Decision

Insight Agent vs Scan Engine

Why agent-based scanning is the primary mechanism for Vault — and where the scan engine supplements.

Primary Insight Agent

  • RPM vulnerability assessment every 6 hours (cloud-side)
  • Process inventory every 15 minutes (continuous)
  • Network connections every 15 minutes (continuous)
  • CIS benchmark assessment every 24 hours (Endpoint Broker)
  • File integrity monitoring (continuous, hash-based)
  • Real-time EDR: process + file + network events
  • Zero credentials needed (TLS client cert only)
  • Minimal performance impact (collection only, no on-node assessment)
  • No inbound ports required (outbound-only TCP/443)
  • Works through Collector proxy for air-gapped environments
  • Cannot perform external TLS handshake analysis
  • Cannot validate port exposure from network perspective
  • Cannot check HTTP security headers on Vault API
VS

Supplementary Scan Engine

  • TLS config analysis on port 8200 (cipher suites, protocol, cert)
  • TLS config analysis on port 8201 (mTLS, internal CA)
  • Full port scan TCP/1–65535 (external perspective)
  • HTTP security headers check on Vault API
  • Custom CIS Vault Benchmark hardening checks
  • Requires SSH credentials (vault-scanner service account)
  • Scheduled scan windows only (daily/weekly)
  • Consumes CPU/memory on target during scan
  • Requires inbound TCP/22 and TCP/8200 firewall rules
  • Scan engine compromise exposes SSH keys to all nodes
Architecture Decision
Insight Agent is the primary scanning mechanism. Scan engine is supplementary only — configured with "Skip checks performed by Insight Agent" to avoid duplication.
Credential Reduction
Agent model eliminates SSH scan credentials on Vault nodes. Scan engine SSH key is used only for weekly SSH config hardening check — not for vulnerability assessment.

Vault API TLS (Port 8200)

11 — Security Hardening

Agent Security Controls on Vault Nodes

Agent confined by SELinux, resource-limited by systemd, and denied access to all sensitive Vault data paths.

systemd Resource Constraints
CPUQuota=10% ← Vault always preempts agent
MemoryMax=256M ← Hard OOM ceiling
MemoryHigh=200M ← Soft throttle
IOWeight=50 ← Below default (100)
Nice=19 ← Lowest CPU priority
OOMScoreAdjust=500 ← Killed before Vault (-1000)
TasksMax=64 ← Prevent fork bomb
